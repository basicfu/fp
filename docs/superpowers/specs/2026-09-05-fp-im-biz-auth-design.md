# fp-im 双认证：fp 令牌与业务方令牌并存

**日期**：2026-09-05
**状态**：设计已定，待写实施计划
**基于**：`2026-09-03-fp-im-design.md`（fp-im 连接网关，已实现并合并）

---

## 一、要解决的问题

fp-im 当前只认两种身份：fp 签发的不透明令牌（走 `fpsdk`）和不需要认证的访客。

接入方往往有自己的认证体系，他们的 client 手里拿的是业务系统签发的凭证，不是 fp 的令牌。现在这类 client 连不上网关。

本设计让**同一个应用同时支持两种令牌**：内部员工可以走 fp 登录，终端客户走业务系统登录，两者在同一个应用下共存。

原设计第十一节预留过这件事，但只写了 JWT 本地验签一种可能，且接口形状没有为多实现共存做准备。本设计选择的是 HTTP 回调，并把接口改成可分派的形状。

## 二、为什么是 HTTP 回调，不是本地验签

本地验签（JWT 之类）零网络往返、不依赖业务方在线，看起来更优。但它要求业务方的令牌是自包含的签名格式。现实中大量业务系统用的是数据库里查的不透明串，改造成本落在接入方身上，而 fp-im 的定位是"降低每个项目重写连接层的成本"，不该反过来要求接入方改造认证体系。

HTTP 回调对任何认证体系都成立，接入方只需要开一个接口。代价是每次握手一次网络往返，以及引入了对业务方的强依赖：那个接口挂了，该应用的业务方令牌就都连不上。这个代价用可选的缓存缓解（第六节），并在文档里写明白。

**走已有的 gRPC 流问业务服务**这条路被否决：握手时本节点不一定持有该应用的服务流，要绕一圈 Redis 问别的节点再等回复，握手就变成分布式等待，业务服务重启期间所有新连接会被卡住。原设计在讨论转发路径时已经否决过同构的方案。

## 三、握手帧与分派

### 3.1 帧的变化

`AuthFrame` 新增一个 `kind` 字段：

```json
{"t":"auth","app":"a1","token":"...","kind":"biz","ua":"...","os":"ios","mobile":true}
```

| 帧的内容 | 走向 | 主体 |
|---|---|---|
| 有 `token`，`kind` 为空或 `"fp"` | fp 的 SDK 验证 | `u:{uid}` |
| 有 `token`，`kind` 为 `"biz"` | 回调业务方 | `b:{user_id}` |
| 有 `guest` | 访客校验（不变） | `g:{uuid}` |
| 其它组合 | 拒绝 4001 | — |

**缺省视为 fp 令牌**，所以现有客户端一行不用改。

**`kind` 是未知值时直接拒绝**，不做兜底猜测。一个拼错的类型说明调用方有 bug，静默降级会让它更难被发现。

**应用没配业务方认证却发了 `kind: "biz"`，同样拒绝 4001。**

### 3.2 客户端可以撒谎，但撒谎无收益

`kind` 由客户端自报，它可以乱填。这不构成安全边界：类型只决定"送到哪个验证器"，不决定"是否放行"。声称是 fp 令牌就送去 fp 验，验不过照样拒；声称是业务方令牌就送去业务方验，同样如此。

### 3.3 为什么是类型字段而不是新的令牌字段

另一种写法是加一个 `biz_token` 字段，与 `token`、`guest` 三者互斥。语义同样清晰，但每加一种认证方式就要往帧里塞一个字段，而类型字段只需要多一个取值。且缺省值天然兼容老客户端。

也否决了**依次尝试**（先 fp 后业务方）：每个业务方令牌都要先被 fp 拒绝一次，而 fp 验证在缓存未命中时是一次网络调用，拿它当探测很浪费；两者都失败时报哪个错也说不清。**按令牌格式猜**更脆弱，业务方换个格式就全崩。

## 四、认证接口的形状

### 4.1 签名改动

现在的接口只收一个令牌字符串：

```go
Verify(ctx context.Context, app, token string) (model.Subject, error)
```

业务方的实现需要转发**原始帧字节**（第五节），那不在参数里。改成传一个请求结构：

```go
// VerifyRequest 是一次身份验证的全部输入。
// 用结构体而不是继续加参数：不同实现用到的字段不同，
// fp 侧只需要 App/Token，业务方侧只需要 App/Raw。
type VerifyRequest struct {
    App   string
    Kind  string // "" 或 "fp" 或 "biz"
    Token string
    Raw   []byte // client 发上来的原始握手帧，业务方回调原样转发
}

type Authenticator interface {
    Verify(ctx context.Context, req VerifyRequest) (model.Subject, error)
}
```

两个哨兵错误不变：`ErrUnauthorized`（凭证无效）与 `ErrUnavailable`（身份服务不可用）。握手代码只需要区分"拒绝"和"稍后再试"。

### 4.2 分派做成组合实现

新增 `internal/im/multiauth`，它本身实现 `Authenticator`，内部按 `req.Kind` 选择下游：

```go
func New(fp, biz auth.Authenticator) auth.Authenticator
```

`biz` 为 nil 表示全局没有业务方认证。单个应用是否启用，由该应用的配置决定，判断在 `bizauth` 内部做。

这样接入层仍然只持有一个认证器，握手代码的形状不变，将来加第三种认证方式时接入层一行都不用动。

## 五、业务方回调协议

### 5.1 请求

```
POST <该应用配置里的 verify_url>
Content-Type: application/json

<客户端握手帧的原始字节，逐字节转发>
```

**网关不添加任何自己的东西，也不带凭据。**

转发原始字节而不是解析后重新序列化，是为了让客户端塞的自定义字段（设备指纹之类）原样到达业务方手里。网关自己仍要解析这一帧，因为要读出 `app` 和 `kind` 才知道往哪转；解析和转发是两件独立的事。

body 大小受握手帧上限约束（`MaxFrame`，默认 1MB）。业务方的接口应当自己设一个更紧的上限。

**已知取舍：这个接口对公网是裸的**，没有任何东西证明请求来自网关。实际风险有限，攻击者要先有一个令牌才能拿去验，而有了有效令牌本来就能直接连网关。真正的用处是批量探测已窃取令牌的有效性。缓解由接入方自己做：接口只监听内网，或在网络层隔离。将来若需要，可在配置里加一个可选的静态密钥，本设计不做。

### 5.2 响应

| 状态码 | body | 网关动作 |
|---|---|---|
| 200 | `{"user_id":"1001"}` | 主体 `b:1001`，放行 |
| 200 | `user_id` 为空、含空字节、或超长 | 拒绝 4001，记警告 |
| 200 | body 不是合法 JSON | 拒绝 4004，记警告 |
| 401 | 任意 | 拒绝 4001 |
| 其它状态码、超时、连不上 | 任意 | 拒绝 4004 |

**失败一律拒绝，没有放行的余地。** 业务方接口挂了就是该应用的业务方令牌全都连不上。不能因为"验不了"就放行，那等于任何字符串都能当令牌。这一条要写进交接文档，免得运维误以为是网关的问题。

400 与 401 的区分：401 明确表示"这个令牌不对"，业务方主动告知，网关据此回 4001 让客户端去重新登录。其它任何非 200 都归入"服务不可用"，回 4004 让客户端退避后重连。这与关闭码的既有契约一致。

### 5.3 `user_id` 的校验

`user_id` 会成为 Redis 键的一部分（`fp:im:{app:b:1001}:conn`），所以必须校验：

- 非空
- 不含空字节（`\x00`）——路由器的内存键用它做分隔符
- 长度不超过 128 字节

违反任何一条都拒绝并记警告。这类校验对 fp 的用户标识现在也没有做，是原设计遗留的缺口（复审记录在案），本次一并补上，两条路径共用同一个校验函数。

## 六、缓存

### 6.1 由业务方决定

响应里可选带一个缓存秒数：

```json
{"user_id": "1001", "cache_seconds": 60}
```

不带、为零或为负都表示不缓存。

**把决定权交给业务方**而不是网关固定一个值，理由是只有业务方知道自己的令牌撤销有多频繁、能容忍多长的失效窗口。fp 自己的令牌验证就是这个模式：fp 在响应里下发缓存时长，SDK 照做。

### 6.2 为什么需要它

网关某个节点崩溃时，它上面的所有连接会在同一时刻重连到其它节点，于是业务方的验证接口在几秒内被打上成千上万次。**这是网关的固有行为，不是异常情况。** 不缓存的话，接入方必须自己为这个尖峰做限流和扩容。

### 6.3 实现约束

- **缓存键是应用标识、令牌、`verify_url` 三个字段的组合**，用结构体做键而不是拼接成字符串。拼接会引入歧义：应用 `a` 加令牌 `1:b` 与应用 `a:1` 加令牌 `b` 拼出来是同一个串，两个应用的令牌就串了。带上 `verify_url` 是为了让热重载把某个 app 切到新后端之后，旧后端对同一个令牌给出的结论立刻失效，而不是继续生效到 `cache_seconds` 过期（整分支终审发现，合入前补上）。
- **每个节点独立的内存缓存**，不走 Redis。缓存本来就是尽力而为，走 Redis 反而给热路径加了一次往返。
- **带容量上限的最近最少使用淘汰**，上限可配，默认一万条。无界缓存会在令牌高基数的场景下吃光内存。
- **只缓存成功的结果。** 失败不缓存：业务方接口恢复之后，客户端应当立刻能连上，而不是等一个负缓存过期。

### 6.4 有意的取舍：已建立的连接不会被重新验证

`cache_seconds` 只影响"下一次握手要不要重新回调业务方接口"，不影响已经建立的连接。验证只发生在握手那一刻：一条连接一旦握手成功，会一直活到空闲超时或客户端自己断开为止，业务方在自己的系统里吊销这个令牌不会让这条连接断开。

这与 fp 令牌的路径不对称：fp 有 `fpauth.OnRevoke` → `hub.OnRevoked` 这条撤销通路，fp 撤销一个令牌会当场关掉持有它的本地连接。业务方令牌没有对应的通路——网关不知道业务方什么时候吊销了一个令牌，也没有机制去问。

**这是有意的取舍，不是遗漏。** 给业务方令牌接入撤销通路，意味着网关要么轮询业务方要撤销哪些令牌，要么业务方主动推一个撤销事件过来，两者都是新的双向接口和新的强依赖，超出了"回调验证"这个最小接口的范围。需要立即踢人的场景，接入方本来就有更直接的手段：server SDK 的 `Kick`（主体 `b:{user_id}`）。这条取舍要写进交接文档，否则接入方会把 `cache_seconds` 误解成撤销窗口。

## 七、主体前缀

新增 `b:`，与现有的 `u:`（登录用户）、`g:`（访客）保持单字符风格。

业务方的用户 1001 是 `b:1001`，与 fp 的 `u:1001` 在 Redis 键上天然隔离，不会互相顶号、不会收到对方的消息。

主体解析有三份实现，**全部要同步**：

| 位置 | 用途 |
|---|---|
| `internal/im/model/subject.go` | 网关侧 |
| `sdk/im/subject.go` | 两个客户端 SDK 共用 |
| `internal/integration/im_parity_test.go` | 断言前两者对同一批输入行为一致 |

配对断言的输入集要扩充，加上业务方主体的合法与非法两种情况。现有输入集覆盖了合法用户、合法访客、大写标识、无连字符、版本位错误、未知前缀、空串。

`sdk/` 不能 import `internal/`，所以这份重复是架构约束下的必然，配对测试是唯一的防线。

## 八、配置

### 8.1 形状

```json
{
  "apps": [{
    "app_id": "a1",
    "app_secret": "...",
    "conn_policy": "replace",
    "conn_limit": 5,
    "allow_guest": true,
    "guest_ip_rate": 20,
    "biz_auth": {
      "verify_url": "https://your-service/im/verify",
      "timeout": "2s",
      "cache_size": 10000
    }
  }]
}
```

**整组为空表示这个应用不支持业务方令牌。** 用嵌套而不是铺平成三个字段，是因为"支持不支持"要能整块判断，铺平之后就得靠"地址是不是空串"这种间接判断。

### 8.2 校验

在 `AppConfig.Validate()` 里，与现有四条规则并列：

- `biz_auth` 存在时，`verify_url` 必填。
- **`verify_url` 必须是 HTTPS**，配了 HTTP 直接启动失败。令牌明文走在请求体里，明文传输等于把所有业务方令牌交给中间人。
- `timeout` 缺省 2 秒，必须大于零。它是**整个请求的超时**，含连接建立、发送、等待响应、读完响应体，不是单独的连接超时。握手本身有 5 秒上限，验证超时必须明显小于它，否则客户端会先被握手超时踢掉，拿到的关闭码是错的。
- `cache_size` 缺省 10000，必须大于零。

沿用现有的失败策略：**任何一个应用的配置非法，整份配置拒绝加载**，不是"跳过坏的、加载好的"。半份配置会让某些应用神秘地连不上，比整份失败难查得多。

热重载机制不变，仍然是每十秒检查文件修改时间，坏文件保留上一份。

### 8.3 为什么不放 Redis、不由 SDK 上报

曾考虑让业务方在 SDK 配置里写上验证地址，建流时上报给网关。它撞上一个硬伤：**客户端和业务服务连的是不同节点**。业务服务连在节点乙就只有节点乙知道地址，而客户端可能连到节点甲，节点甲上一条业务服务流都没有，无法验证。

解决它要么把地址同步进 Redis，要么放配置。放配置最简单，没有任何新状态，每个节点独立读到同一份，也没有灰度发布时新旧实例上报地址不一致该信谁的问题。

## 九、失败与关闭码

不新增关闭码，复用既有契约：

| 场景 | 码 | 客户端应该 |
|---|---|---|
| 令牌无效、类型未知、应用没配业务方认证、`user_id` 非法 | 4001 | 不自动重连，去重新登录 |
| 业务方接口超时、连不上、返回非 200 非 401、200 但响应体不是合法 JSON | 4004 | 退避后重连 |

响应体不是合法 JSON 归入"服务不可用"而不是"凭证无效"，因为那是业务方的接口坏了，不是客户端的令牌有问题。让客户端退避重连，等业务方修好。

4001 与 4004 的分界是"这是你的问题"还是"这是我们的问题"，与 fp 令牌路径的语义完全一致。

## 十一、测试要点

- **分派矩阵**：四种帧组合各自走到正确的验证器，未知类型被拒。
- **业务方回调**：200 正常、200 但 `user_id` 非法、401、500、超时、连不上，六条路径各自映射到正确的关闭码。
- **原始字节转发**：客户端塞的自定义字段原样到达业务方，网关不增删。
- **缓存**：带缓存秒数时第二次握手不再发起 HTTP 调用；不带时每次都发；失败不进缓存；容量上限生效。
- **配置校验**：HTTP 地址被拒、缺地址被拒、超时与容量的默认值填充。
- **主体前缀**：三份实现对同一批输入行为一致，`b:` 的合法与非法输入都覆盖。
- **回退验证**：每条关键性质写完后把实现改成缺陷版本，确认对应测试变红。这是本项目的既有要求，前一批任务里反复出现过"测试名字承诺的性质其实没被断言"。

## 十二、本设计不做的

- **配置进控制台 UI。** 现在仍是配置文件。控制台配置需要 fp 侧存储、接口，以及网关从 fp 拉取配置的链路，那是独立的一块，且撞上"应用密钥库里只有哈希、读不回明文"的结构性障碍。
- **验证接口的鉴权。** 见 5.1 的取舍说明。
- **本地验签实现。** 接口形状已经为它留好位置，将来加一个实现即可，接入层不用动。
- **负缓存。** 失败不缓存，见 6.3。
